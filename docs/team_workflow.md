# 三人、三个 Codex 的最小协作方式

三人各用自己的 Codex，共享项目文件；不必连接账号，也不固定谁只能建模、编程或写论文。每阶段由当时最合适的人承担工作，一人临时整合公共题意和论文，避免同时覆盖。规则以 [AGENTS.md](../AGENTS.md) 为准。

## 接活、交接、接收

- **接活**：“读当前题意和快照，找出现在最值得我交出的一个结果或决策，说明依赖与编辑范围，然后实际推进。”
- **交接**：“把准备采纳的结果交给队友，给权威文件、评价口径、复算方式、真实验证和一句有证据支持的结论。”
- **接收**：“确认队友结果仍适用于当前模型，做最关键的独立核查，再更新现有快照和论文；没有人工核验就如实标明。”

这些话是可直接给 Codex 的工作要求，不是学生需要反复填写的表格。只为准备采纳、比较、写入论文的关键成果整理交接，普通探索不另办手续。

## 怎样同时推进

先看依赖，再分工。例如，一人建立最小可运行模型，一人从题面独立检查假设与约束，一人整理数据并起草已有证据支持的内容；模型稳定后再重新分配。没有成立的共同评价器时，不让三个 Codex 各自猜一套后续小问接口。

已有 `docs/project_concept.md` 和 `docs/project_handoff.md` 就继续使用。若尚无这些文件，先在现有项目文档写一小段题意快照：输入、输出、目标、主要约束、当前假设和下一步；有了实际内容再确定固定承载位置，不先铺空模板。

接活时明确改哪些文件，共享文件由当期整合者接收修改。任务分支保留清楚的提交；二进制论文同一时段只让一人整合。上游模型改变时，指出哪些结果需要重算，不要求无关队友停工。

达到可行解、提高计算精度、改善题目目标、整理交付是不同阶段。程序达到迭代上限不能说收敛；仍在改善时，应结合剩余资源和其他小问的需要决定下一步，把决定与最短证据留在现有快照中。

## Skills 与结果

可复用工具维护在独立的 [CUMCM Skills 仓库](https://github.com/MrRoam/CUMCM-skill)。取得包含所需工具的已核验提交后，按该版本的 README 安装；三人固定同一个完整 commit，各自在自己的 Codex 里确认能发现。安装、更新与完整性检查的命令只维护在 Skills README，本项目不复制一套。

结果凭据可帮助发现已登记文件变化、追溯实际指标；它不证明依赖登记齐全、数学正确、实际运行或人工核验。评价器要包含主脚本调用的关键模块和配置。接收者仍需做能推翻当前结论的检查，例如独立约束复核、手算小例子或从原始结果重建论文数字。只变动注释不一定改变数学口径，需查看差异，不能把文件哈希当成语义判断。

正式采用前，让队员亲自解释一个影响结果的假设或复核一项关键数值；不会时让 Codex 围绕这个判断解释并协助操作。一次小检查不能冒充对整份成果的人工审查；保留尚未核验的范围。另一个 Codex 的复查仍属于机器检查，实际采纳、修改与核验按环节记录到 [AI_USAGE.md](../AI_USAGE.md)。

## 赛前与正式赛期

赛前可使用 GitHub 任务分支和 PR 演练；正式赛期先核对当届规则。2026 [参赛规则](https://www.mcm.edu.cn/html_cn/node/9d8e511fe7a1447b35f53a82c908e2e0.html)明确限制 GitHub 等平台上的赛题交流，不能自行认定私有仓库豁免。

当前保守方式是赛前冻结 Skills，赛期保留本地 Git 的提交与合并，用队内文件传递已核对的修改；不要向队外公开、接收讨论或在 GitHub 同步当届赛题内容。这是保守工作选择，不是对传输方式的官方认证。离线交接操作见所用 Skills 版本中的队内交接说明。

2026 [AI 使用规定](https://www.mcm.edu.cn/html_cn/node/fef94648f2836ab6cc81586f4c38512b.html)自 9 月 1 日起试行，允许 AI 工具与智能体，但核心建模分析须由参赛队主导，AI 参与内容须逐项人工审查与核实。论文声明和支撑材料的要求见 [AI_USAGE.md](../AI_USAGE.md)。

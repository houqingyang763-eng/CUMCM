# CUMCM 数学建模竞赛协作仓库

本仓库用于全国大学生数学建模竞赛的团队协作。项目结构围绕“输入、探索、正式计算、生成结果、论文、提交物”组织，目标是让每个进入论文的结论都能追溯、复核和重新生成。

## 目录说明

```text
CUMCM/
├─ inputs/
│  ├─ official/       # 赛题、官方附件、官方数据与模板
│  └─ external/       # 团队自行收集并实际使用的数据
├─ experiments/       # 候选模型、探索脚本、Notebook 和一次性试验
├─ src/               # 已整理、已验证、可复现的正式代码
├─ outputs/           # 代码生成的图、表和数值结果
├─ paper/             # 唯一权威论文源稿及其引用文件
├─ submission/        # 从冻结版本生成的最终提交文件
├─ docs/              # 长期有效的设计说明与实施计划
├─ AGENTS.md           # 人和智能体共同遵守的稳定协作契约
├─ DECISIONS.md        # 重大技术、模型与口径决策
└─ AI_USAGE.md         # AI 工具使用和人工核验记录
```

各目录遵循以下边界：

- `inputs/official/` 永远保持官方原件，不在原文件上清洗、改名或覆盖。
- `inputs/external/` 只放建模实际使用的外部数据，并记录来源。
- `experiments/` 允许快速试错，但其中的结果不能直接作为论文正式依据。
- `src/` 是正式计算的唯一代码来源，使用仓库相对路径，并将结果写入 `outputs/`。
- `outputs/` 中用于论文的图、表和数字必须能由代码重新生成，不手工修改。
- `paper/` 只维护一份权威正文，不同时维护 Word 和 LaTeX 两套正式版本。
- `submission/` 是发布区，不在其中编辑源码、数据或论文。

## 工作流

```text
inputs → experiments → src → outputs → paper → submission
```

1. 将官方材料放入 `inputs/official/`，将实际使用的自采数据放入 `inputs/external/`。
2. 在 `experiments/` 中比较候选模型、参数和处理方法。
3. 模型被团队采纳后，将完整、可复现的实现整理到 `src/`。
4. 从 `src/` 运行正式计算，把论文采用的结果生成到 `outputs/`。
5. 人工检查公式、单位、边界条件、随机种子和关键数字后，再将结果引入 `paper/`。
6. 从一个明确的冻结 Git 提交生成 `submission/` 中的论文与支撑材料。

## Git 协作

以下 GitHub 推送与 PR 方式适用于赛前演练等允许的场景。2026 正式赛期先按[协作说明中的官方规则](docs/team_workflow.md)确认边界；当前保守使用本地 Git 与队内文件传递，不自行假定私有 GitHub 仓库豁免。

- 不直接向 `main` 推送。每项工作从最新 `main` 创建短生命周期分支。
- 一个分支只处理一个明确问题，使用小而完整的提交并频繁同步。
- 创建 Pull Request 前确认：工作目标已完成、相关验证已通过、论文与结果一致、没有已知冲突或未说明风险。
- 修改 Word、Excel 等难以合并的二进制主文件前，先在团队内指定当期唯一整合者。
- 不按成员建立私人目录；任务负责人和修改范围通过任务系统或团队沟通明确。
- 不使用 `最终版_v2`、`最终版_真的最终版` 等副本管理版本，版本历史交给 Git。

## 完成标准

一项会影响论文结果的工作只有在满足以下条件后才算完成：

- 输入来源、数据口径、参数和模型假设已经说明；
- 正式实现已经从 `experiments/` 晋升到 `src/`；
- 图表和关键数字可从代码重新生成；
- 另一名成员能够复核核心公式、约束和结果；
- 重大选择已记录到 `DECISIONS.md`；
- AI 参与情况及人工核验已按需记录到 `AI_USAGE.md`；
- 变更内容、验证方法和剩余风险已经交代清楚。
